Can It Play DOOM?

Yugaantar 2026 · DevForge Track 1 · Project brief

USP: a neural agent that builds its own map, and is taught before it is left alone

The observations contain no position, no heading and no map. Our agent estimates its own pose from its own actions, draws a map of the level as it explores, and reads that map through a learned planning module. It is trained by imitation of a training-only teacher with DAgger, so it also learns to recover from its own mistakes, with a reinforcement-learning term and a curiosity reward in the same loop. Every action in the submitted agent comes from the trained network.

  • Self-built spatial memory. Heading from the agent's own turn buttons (the engine's turn ramp, measured), position from the velocity in vitals, rays painted into an occupancy grid. No privileged data.
  • It sees what the rays cannot tell it. Locked-door colours and the exit pad are read from the frame and written into the map (page 2). Both were added without retraining and measured on held-out levels.
  • Levels in the organisers' own format. We decoded the template's test maps and generate unlimited solvable levels across all four tiers.

Neural architecture (1.47M parameters, about 6 ms per decision on one CPU thread; limit 40 ms)

64 rays ───────────────► circular 1D CNN ───────────────┐
visible entities ──────► MLP + type embedding, attention ┤
vitals + last action ──► MLP ────────────────────────────┼─► GRU(256) ─► direction head ─► 23 button combinations
own map (fine + wide) ─► 2D CNN + learned planner (x8) ──┘                (+ value and helper heads)
ModuleDesign
RaysCircular 1D CNN over the 64 rays (distance, near-ness, hit type); wraps around 360°.
EntitiesPer-entity MLP with a type embedding, masked attention pooling plus max pooling: any number of enemies and items.
Spatial memorysubmission/slam.py: occupancy grid (free, wall, door, locked door, visited, frontier) in the agent's own odometry frame. The network reads a fine 32×32 egocentric crop and a zoomed-out 16×16 one.
Learned plannerA small convolution applied 8 times over the map, value-iteration style, so "something worth going to is over there" can spread through free space. All weights are trained.
Recurrent coreGRU (256), reset before every map.
HeadsWhich way to go (16 directions or none), then 23 button combinations conditioned on it, a value head, and helper heads (the teacher's goal type; "locked door seen") that force the memory to hold task-relevant facts.

Safety. Inputs are sanitised, act() is guarded so it always returns a valid action, inference runs on CPU with a warm-up pass in __init__. On the official validator: 2 s initialisation, 6 ms median step, exit reached on the test map.

Training and exploration pipeline

  • Map generator (training/mapgen.py): arenas, multi-room mazes with dead ends, key → locked door → exit chains, multi-lock gauntlets; sizes, monsters, key colours and door placement randomised; every level checked for solvability.
  • Teacher, training only (training/teacher.py): frontier exploration, key → lock → exit planning, door handling, combat. It lives outside submission/ and is never imported by the agent.
  • DAgger (training/dagger.py): the network drives, the teacher labels every state it visits, data is aggregated across rounds; later rounds sample tiers 3 and 4 more heavily.
  • Reinforcement-learning term in the same loop: each game is scored with a shaped reward that mirrors the scoring categories; the value head regresses the return and actions that did better than predicted are reinforced (self-imitation).
  • Exploration and curiosity. The frontier layer of the map marks where unexplored space begins, and the reward includes an intrinsic bonus for entering a cell of the agent's own map that it has never stood in.
  • Local scorer and diagnosis (scorer.py, diagnose.py): our estimate of the official categories from privileged state, and a per-tier breakdown of how far each run got and where its time went.

Results and what makes it work

It completes the full chain: explore, fight, find the key, unlock, exit

Levels built in the organisers' sample style (64-unit cells, same doors, keys and exit pad), network playing alone, 8 to 12 seeded runs per level:

LevelWhat it demandsExit reached
Organisers' sample layoutpick up key, open locked door, reach exit8 / 8
Four rooms (tier 2 style)explore, open three doors, find the exit in the far room8 / 8
Key in a side room (tier 3 style)leave the main path for the key, come back to the locked door, exit8 / 8
Two keys, two locks, monsters (tier 4 style)two key and lock stages in order, with combat11 / 12
Deeper gauntlet (tier 4 style)longer route, two locks, more monsters8 / 12

In every tier 4 run the agent collected both keys. On the official validator it reaches the exit of the test map in 98 steps, and it does so inside the organisers' Docker image under the evaluation limits.

It holds up on levels far larger than the samples

As a stress test we ran 384 generated levels never used in training, with routes of up to 100 cells and rooms up to twice the sample scale. There the agent picks up the key in 95% of tier 3 levels and opens the locked door in 81%; on tier 4 it averages 1.7 keys and 1.4 locked doors per level; and it finishes about two thirds of the combat and exploration levels. Our local score (our own estimate of the official categories) rose from 1083 to 1198 with the three perception additions below, using the same network weights.

Three additions that came from diagnosis

We measured where runs broke instead of guessing: on gauntlet levels an earlier checkpoint held the first key but spent 14% of its time at locked doors it could not open, because the rays say "locked door" but not which colour. That led to three additions, each verified on held-out levels:

  • Door colours. Each locked door's red, blue or yellow grille is read from the frame, using the depth buffer to keep only pixels on that door. Until the agent holds the matching key, that door appears in its rays and its map as a wall; it turns back into a locked door the moment the key is picked up. The agent stops wasting time on doors it cannot open.
  • Exit pad. The exit is in neither rays nor entities. Its red floor is found in the frame, placed with the depth buffer and written into the map as a place worth going to. Blood, corpses and fireballs are rejected because an upright sprite has one depth while a pad on the floor spans a range, and damage-tinted frames are skipped.
  • Jam recovery. Doors are 64 units wide and the player 32. If the agent pushes forward without moving and is not waiting at a door, forward is withheld for a few steps and the network's next choice frees it.

In all three the network still makes every decision.

Built to be scored: fast, small and safe

5 ms per decision on one CPU core (limit 40 ms), 0.73 GB of memory (limit 8 GB), 3 s to initialise (limit 60 s), a 6.5 MB repository (limit 1 GB). Every action is guarded, so a fault can never freeze the player for the rest of a map, and inference runs on CPU, so the agent does not depend on the shared GPU. validate.py passes locally and with --docker.

Where we take it next

  • A stronger RL stage: PPO fine-tuning anchored to the current policy by a KL penalty, the approach that won comparable key-and-door challenges, to push past the teacher on the longest gauntlets where time is the constraint.
  • A goal-picking layer on top of the map, so "take this key to that door" is an explicit learned decision.
  • More map styles: switch-operated exits and lifts, and training on hand-made levels alongside generated ones.
